# Login and scene regression

English | [简体中文](login-scene-regression.zh-CN.md)

`LoginSceneRegression` drives the real request handlers over an in-memory KCP connection to check login, RSA, scene loading, teleporting and most gameplay that runs on top of a scene: missions, characters, the Simulated Universe, challenges and activities. Run it after changing login, scenes, missions, lineups, characters or any of the features listed below.

Project: [`scripts/LoginSceneRegression/`](../../scripts/LoginSceneRegression/)

## How to run

From the repository root:

```powershell
dotnet run --project scripts/LoginSceneRegression/LoginSceneRegression.csproj -c Release
```

Options:

- `--legacy-cache <pre-upgrade Resource.bin>` additionally checks deserialization and the staleness check of a cache from before an upgrade.
- `--resource-cache <newly generated Resource.bin>` uses a cache regenerated from raw resources instead of `Config/Resource.bin`, for example before replacing that file. The cache is only copied into the temporary directory; the source file is not rewritten.

## Prerequisites

- The regression uses random RSA keys, a temporary SQLite database and an HTTP service that listens only on the local machine. It does not read the operator configuration, connect to a production server or rewrite an existing database.
- The scene tests read a copy of the current `Config/Resource.bin` and do not regenerate the cache.
- The character trial cases need a cache with `AvatarDemoConfig.StageType`/`SPList`. If the cache lacks these two fields, the regression stops with an explicit error in the character trial section.
- The path of the temporary artifacts is printed when the run ends.

## What it covers

Most checks live in `scripts/LoginSceneRegression/Program.cs`. `MainFixRegression.cs` holds the common Rogue query, minigame data handlers, lineup slots and favourites, Trailblazer current path, relic preset, dungeon/Raid exit and avatar frame display checks; other larger areas have their own files, named below. All of them run from the same entry point, with the temporary SQLite database and in-memory KCP, and never touch a real player database.

### Login and RSA

- Shield and the new and old Passport: three RSA paddings, 1024- and 2048-bit keys, mismatched keys, missing or invalid private keys, malformed ciphertext, strict UTF-8 and plaintext compatibility.
- A decryption failure must return an error before login and before automatic registration. Encrypting for the same account several times with random padding must yield only one account.

### Protocol details

- Numeric tags: `SceneMapInfo.floor_id=14`, `retcode=6`. Failure return codes are encoded on their own; forced field mappings take precedence over inference from older versions; original and semantic name scopes are merged.
- `CommonRogueQueryScRsp`: the query type is the field number of the `CCKJAEDDDCL` oneof branch, read from the current generated protocol code. The feature-unlock branch `CCKJAEDDDCL.BBEKBJPHEJKFieldNumber` is `15` in 4.5, `1` in 4.6, `10` in 4.7 and `15` in 4.8. Only that branch carries the unlock set, in request order and with duplicates; the other three query types stay without a branch, and no state is invented for them.
- `SocialPlayGetDataCsReq`, `PetMarbleGetDataCsReq` and `PetMarbleGetCycleTrialPetsCsReq` have handlers, registered through the source-generated opcode table. Every singular sub-message in their responses (recursively, 5 levels, excluding oneofs and lists) is sent as an empty message instead of the empty body of an unhandled request, so the client never receives null. No oneof is chosen and no list item is added.
- Social-play room owner (`SocialPlayRoomOwner` in `MainFixRegression.cs`): `SocialPlayPreCheckEnterRoomCsReq` and a social-play `EnterSceneCsReq` naming a uid with no account return `RET_FRIEND_PLAYER_NOT_FOUND`, leave no pending or current room, and neither save a `TrainCakeCatchData` row nor add a `UidInstanceMap` entry for that uid. A pre-check for an existing offline account succeeds with an unsaved default room view.

### Scene loading and floor state

- Floor save conditions: the AND/OR/NOT truth table, every comparison operator, and equality semantics when the cache omits the comparison operator.
- The rule that sets activity floor variables to `1` is restored: on Town/Maze floors with an associated activity mission, variables whose resource default is `0` are set to `1` (except `*_IsHidden`); explicit saved values still take precedence; nothing is written to the player save. With the mission system enabled, `SceneStateByMainMission`/`WorldStateByMainMission` are no longer forced to `1` and keep the resource default (the official server sends `0` for `20001001`), so the value saved by the story decides; with missions disabled they are still set to `1`. Checked on Exalting Sanctum (长乐天) `10202001/170` (Pure Fiction entrance) and Dreamflux Reef (流梦礁) `10304001/145` (Apocalyptic Shadow entrance): actual entity creation, the teleport payload, login recovery, repeated sync and save overrides, not just the group switch.
- Map group response, against the official 4.6 server: on floor `10001001`, client NPC group `4` and automatic mission trigger group `5` enter `maze_group_list` according to their mission conditions even without server entities. `client_group_mission_info` follows the scene mission state of the same floor: the field is visible when prerequisite main mission `1000300` is finished and `1000301` is in progress, and group `5` unloads after `1000302` is finished. Client mission state is checked on the current and other floors; on the current floor, groups already loaded during the delayed unload are kept; real player saves are not changed.
- The mission state list is derived from the client group load/unload conditions and their associated missions. For floor `10001001` it matches, item by item, the 32 sub-missions in the official 4.6 entry snapshot; the in-progress story dialogue `100030103` no longer appears in the entry snapshot and is sent only through the mission sync stream. The derivation also matches the sub-mission sets of the other captured floors.
- Xianzhou anomalous props are excluded precisely: the two `PCOnly` capture exclusions Central Starskiff Haven (星槎海中枢) `10201001/280/300001` and Exalting Sanctum `10202001/208/300001` are kept, and the older Android-fix exclusions `10202001/144/300003` and `10202001/208/300002` are restored. Initial load, direct creation and forced load follow the same rule; the empty groups `208` (Exalting Sanctum) and `280` (Central Starskiff Haven) are not loaded twice.
- Only the anomalous atmosphere group Exalting Sanctum `10202001/169` is excluded, and leftover groups and entities are removed on sync. There is no global exclusion based on `IsHoyoGroup` combined with `Atmosphere`. Ordinary non-initial props, NPCs, other atmosphere groups and the elevator in group `8` of the storage section (储物舱段) remain available. The open-all rule for activity floors is unchanged; teleport, login recovery and repeated sync do not resend the anomalous content. The compatibility list uses the floor/group/instance IDs in the cache, so the current cache does not need rebuilding.
- Login-recovery scenes and teleport scenes both carry the 4.5 initialisation values. Both ends of the in-memory KCP connection check the order `1491 → EnterSceneByServerScNotify → EnterSceneScRsp`; same-map moves, silent builds, invalid teleports and the login snapshot do not send a scene-switch boundary by mistake.

### Teleports, dungeons and temporary scenes

- Teleport success and the cross-map flag are returned separately. Invalid entrances, missing floors/anchors/maps and an aborted recursive load no longer report success. Same-map teleports, reloads and teleports to the position saved for a story line keep working.
- Leaving a dungeon whose resource configuration or run record is missing neither throws nor goes unanswered. It returns to the original entrance first; an invalid entrance, or an old return point that itself points into a dungeon, falls back to the default spawn point. At login, an orphaned dungeon position is repaired before the scene loads, while normal runs and positions held by a story line are kept. The reset notification keeps an empty item list, and a repeated exit is only acknowledged.
- Temporary scenes (Raid): if an in-progress Raid in the save is no longer in the current `RaidConfig`, logging in again abandons the run, deletes the record and returns to the entry point (`OldEntryId`/`OldPos`); leaving that Raid also returns to the entry point and deletes the record. If the run record is lost, leaving returns to the default spawn point `2000101`. Raids that do exist in `RaidConfig` are still restored at login by default. The `RaidInfoNotify` used for the reset keeps an empty `item_list`.
- `ServerOption.ResetLocationOnLogin` (default `false`, editable on the admin settings page): when on, every login abandons an in-progress Raid (deleting the record) and challenge and ChallengeTierce (星启) runs, and resets the position to the default spawn point `2000101` before loading the scene. It has no effect while a story line is in progress.

### Scene entities and combat entry

- Summon field buffs (real monsters on `20001001`; Cyrene (昔涟) `141501` → summon `14151` → enemy `141502`): buffs cast by the summon use the summon's own entity ID as `BuffSummonEntityId`, keep the resource duration `500`, are separate instances per enemy, and refresh to `1` when leaving the field. A summon created by a modifier of a limited-duration maze buff is sent with `LifeTimeMs=-1`, is destroyed when that buff is removed and takes its cast buffs with it; when the owning buff is permanent a 45-second fallback still applies. A summon with `RemoveMazeBuffOnDestroy=false` (`14101`) keeps the buffs it cast after it is destroyed.
- Monster attack on the slope of the containment section (收容舱段), using the real floor `20002001`, group `5`, instance `200007` and the request handlers over in-memory KCP: a projectile without a hit target (official 4.6 seq 9469-9471) only returns an ACK and neither creates a battle nor clears scene summons. The attack source always comes from `attacked_by_entity_id`; a `cast_entity_id` that happens to equal a character entity ID is not turned into a player attack. Also covered: invalid sources and targets, normal player attacks, the ambush buff and monster ID when a monster really hits the player, a repeated request reusing the battle, and the compatibility path for a missing monster ability.
- On the same floor, Archer's technique starts the encounter when the projectile impact reports the monster only in `hit_target_entity_id_list`. The response contains the monster and opening buff once, including when both projectile tags are present. Expiration without an impact leaves the player outside battle. With the 4.7.51 cache, Ellen and Astra have no exported scene abilities. Their normal attacks still start the encounter and carry the full lineup when a hit also ends the projectile. The cases require the three avatar rows in the cache.
- `/spawn`: argument parsing (`lv`/`hp`/`s`/`x`/`r`; waves split by `/`, `|` or `\`, automatic splitting at 5 monsters per wave; invalid IDs reported together) and ID resolution (`monster`, NPC monsters, battle MonsterIDs mapped through templates, props, battle-only monsters). With no monster configuration on Exalting Sanctum it reports that there is no template. On the first Maze floor in the resources with a usable monster group, a spawned monster borrows the group, instance and EventID of a loaded group, with an offset radius and zero rotation. In battle, custom waves replace the stage waves (wave numbers 1..N, fixed stage, level and HP overrides); with only an HP override the stage waves are kept. A battle that mixes in real monsters still counts for missions. Spawned props are Open, carry no template event, chest or interaction, and their state is not saved. Invalid IDs, a missing stage, the entity limit, a missing ID and Simulated Universe scenes spawn nothing.

### Characters

- Costumes, through the real dress and undress requests: dressing marks the player for saving and first sends a character sync that keeps the level, light cone and relics, then the result. Missing characters, unknown or unowned costumes and costumes of another character are rejected; a repeated dress is only acknowledged; restoring the default costume does not depend on the skin unlock dictionary. Equipment ownership and battle serialisation are checked with real inventory items; after reading the character back from SQLite and logging in again, the chosen costume and equipment survive a floor change and a re-login.
- With Aeon ★ Aha in the resource cache, `/giveall skin` grants Star Lotto (`1151101`) and syncs the unlock once. The server accepts the dress request after the grant, and the unlock is still present after loading it from SQLite and logging in again.
- Duplicate base character records: old saves can contain several records for the same base character (a real log showed Cyrene `1415` with one levelled record and five empty ones). The login snapshot keeps, per base character ID, the first record, the same one the server's `GetFormalAvatar` picks, so later empty records do not overwrite costume, level and equipment. The stored records are not deleted or merged; no migration, cache replacement or account rebuild is needed. Adding a character or unlocking a path again no longer appends the same base character, nor resets saved path data.
- Character quick level-up, through the source-generated opcode table, request parsing and in-memory KCP. Official 4.6 capture seq `36813-36829` and the dumper's `cmdid-registry.txt` confirm that request enum `KELLLHMHFHL` maps to message `EKLIDIDKFHC` (cmd 376) and response enum `MILFFHPMLMN` to `PMEMIDKDAFG` (cmd 357). 4.7 uses cmd 355/341 and 4.8 uses 332/395; the generated messages with the same identity and their current field numbers are used directly. In the request, `IGOOJKMPMDC` and `KLMIBJIKIBB` are the target level and target ascension, `BACAOLDADMC` is the EXP-material cost and `OAINNDAHIMG` is the separate ascension cost.
  - Covered: an ascended character levelled to 30 with 8/6/7 EXP materials; a level-20 unascended character going to level 30 / ascension 1 in one request that pays both the EXP materials and the ascension cost from the resource table; a refund of 2 of item 211 (character EXP material); existing character EXP counts towards the refund.
  - The server validates every cost, the inventory, the level cap and the Trailblaze Level / Equilibrium Level requirements first; on success it syncs the character, credits and the final material balance before replying.
  - Failure paths: missing character; missing credits, EXP materials or ascension materials; an understated ascension cost; duplicate material rows; quantity overflow; using light cones or light cone EXP material instead of character EXP material; not enough EXP; an invalid target. Repeated or concurrent identical requests are charged once.
- Light cone quick level-up: the real `EquipmentQuickUpCsReq` handler over in-memory KCP checks the current command (513/517 in 4.7, 548/529 in 4.8) and field identity. Covered: the logged 5-star light cone 1→20 (5 of material 223); a mix of 8 of 221 + 10 of 222 + five 3-star fodder light cones; and official 4.6 seq `36859`, a 4-star light cone 20→30 / ascension 1. Credits, ascension materials, the EXP refund, the fodder-deletion notification and the target light cone sync all arrive before the response. Also checked: protected or equipped fodder, the target itself, duplicate or missing unique IDs, invalid or overflowing quantities, wrong materials, not enough EXP/inventory/credits, the ascension cost and Equilibrium Level limits, ascension-only requests keeping the existing EXP, and repeated or concurrent requests charging once. Every failure leaves the player state unchanged.
- Trailblazer paths: in the resources, Trailblazer paths pair odd (male) with even (female). The save keeps the paths of both genders, but the path list and `BasicTypeIdList` in `GetAvatarDataScRsp` and `PlayerSyncScNotify` only carry the current gender. Switching path normalises by gender and returns the ID actually stored; another character's path cannot be applied to the Trailblazer; `/hero type` rejects non-Trailblazer paths; switching gender keeps the saved paths.
- Trailblazer current path repair: it runs after mission-switch overrides take effect, so it does not decide a gender for a new story account that has not chosen one yet. A male current path on a female save becomes the matching female path; a non-path ID falls back to an owned path of the same gender, and the path list in `GetAvatarDataScRsp` includes it. Missing current path data and a stale `CurBasicType` are repaired too; the repair is idempotent and leaves normal data unchanged.
- `/giveall avatar`: without arguments, owned characters keep their level, eidolons and current path, and new characters are level 1 / eidolon 0. An explicit `r` writes all paths the character owns without changing the level; an explicit `l` does not change eidolons. The Trailblazer unlocks only the paths of the current gender.
- Relic presets: creating one requires an owned character and owned relics. Unknown relics, unowned characters, empty plans, updates with no content or invalid relics, and updates that change nothing are rejected; renaming works. Create, rename and delete each trigger a save on their own and are verified by reading SQLite back, without relying on another operation marking the player dirty.

### Lineups

- Ordinary lineups `0..8` are filled in by index (also in old saves with missing indexes or with extra lineups inserted first); the `index` sent matches the slot index and extra lineups are kept. If the current lineup points at an empty slot, the non-empty ordinary lineup with the lowest index is used.
- Favourites: `MarkPresetLineupCsReq` replies with `SetTeamFavourite` (cmd `773` in 4.6, request/response `762/780` in 4.7, cmd `721` in 4.8) and saves the favourite flag. Valid changes persist; extra lineups and indexes outside the ordinary lineups return `RetLineupNotExist`.
- Trial character virtual lineups: removing the last trial character dismantles the virtual lineup, restores the player's own lineup, and notifies the client in the order `ExtraLineupDestroyNotify → SyncLineupNotify`.

### Missions and tutorials

- Mission dialogue: for a player with the mission system enabled, `FinishTalkMissionCsReq{talk_str:"0"}` sent on the floor of the tracked main story's only Talk completion gate (`1010202/101020206`) is only acknowledged and completes nothing; once the client reports its own dialogue string the sub-mission completes normally.
- Qlipoth Fort (克里珀堡) main story floor changes: the real `FinishTalkMissionCsReq` over in-memory KCP advances `101020102 → 101020103` (entering) and `101020104 → 101020105` (leaving). When follow-up missions are accepted, mission scripts can nest teleports and complete EnterFloor gates; aggregated notifications use the actual state and progress at send time, so a gate that has already sent Finish cannot be overwritten by an old Doing snapshot. Against official 4.6 seq `20633–20654`: after leaving, the player stops in the Administrative District `101010102 / 10101001`, the follow-up `101020106` is accepted, a repeated dialogue is only acknowledged, and the player is still in the Administrative District after the hidden performance mission `101020114` completes.
- Tutorial dismissal: free-exploration pop-ups whose trigger condition contains `OnMazeMainPage` (for example `3006 → 1000511`) require the target mission to be finished; an in-progress target is not enough. In-battle tutorials (for example `1001 → 1000101`) still accept in-progress or finished. `TutorialFinish` recursion decides strictness from the target tutorial's own trigger condition.
- Main mission start conditions: `AcceptMainMissionByCondition` requires both `TakeParam` and `BeginParam`. After `1010403` is finished at Trailblaze Level 11, `1010502` is only `Prepared` (shown as locked in the mission list, no sub-missions started) and is accepted automatically once EXP raises the level to 13. An empty or `Auto` `BeginParam` is not a restriction.

### Simulated Universe (classic Rogue)

- Compatibility: `MapEntranceLD.json` is included in the entrance resources; the classic Rogue 904 map can be generated completely from the site room pool; ChessRogue picks the complete default branch when the start packet omits the dice-face branch; the RogueMagic query contains non-empty areas and the required nested information; the Divergent Universe lobby entrance and badge are open by default when there is no save.

- Leaving: a won but not yet left run is discarded at re-login while login still restores its room scene. `LeaveRogueCsReq` then does not settle and returns straight to the lobby (first `1491`, then the success response with the lineup and lobby scene, and the extra lineup cleared). Outside a Simulated Universe room it still returns a state mismatch.

- Room changes on the same floor keep each character's scene entity ID and allocate new monsters and props after the old scene's highest ID, so a character ID the client still uses is never reused for an invisible wall. - Trial Trailblazer IDs: a trial Trailblazer can resolve to another base ID for the current gender. Lineup resolution now corrects the trial slots and leader ID to the actual trial character, also for already-saved mismatched lineups; the regression checks valid character slots and leader buff indexes in every battle on all three levels. The owner `-1` of team-wide blessings (`4294967295` on the wire) keeps its global meaning.
- Re-login mid-run restores the saved lineup of the unfinished run: only when the saved entrance matches the current Rogue room, `LineupRogue` is restored after the generic temporary-lineup cleanup and before the scene loads. Existing lineups keep technique points and the HP and energy of characters in the extra lineup; saves already switched back to the ordinary lineup by the old login path select the saved story trial lineup again. The regression re-initialises and logs in a real player twice, then checks through the real attack handler that all four tutorial battles still use the trial characters and that the ordinary lineup is unchanged.

### Challenges

### Social features and commands

- Friend requests: accepting or refusing a uid that never applied changes neither player; a received apply with no matching sent apply is not accepted and is dropped; a real apply can only be refused by its recipient, and accepting it makes both players friends and clears both apply lists.
- Global chat: the default contact uid `98` is shown next to the command bot, online and pinned, and friend requests to it are rejected; its profile is found by exact uid. Messages are forwarded from that contact to every recipient (including the sender) as `[nickname / uid]: content` and do not go into the command bot conversation. Empty messages are ignored; over-long messages and rate limiting reply only to the sender and are not forwarded; the sliding window counts each sender separately. Each player's history is trimmed to `MaxHistory`, with a welcome message at the end. If the uid collides with the command bot or the feature is off, the contact disappears and nothing is forwarded.
- `/language`: the console cannot pin a language. Aliases are case-insensitive and only languages with a file in `Config/Languages` are accepted. After pinning, replies use the new language, and `PlayerCommandSender` uses the pinned language; `auto` clears it and replies follow the client language again. The pinned value is written to the `Player` table; old tables get a nullable `LanguagePin` column automatically and read as not pinned.

### Save data compatibility

- `LineupInfo.IsFavourite` is appended after the original five MemoryPack members. - Before deploying, stop the server and back up the player database named in the current configuration. Back up SQLite only after the server has stopped, including any remaining `.db-wal` and `.db-shm` files, and keep the old program. An old program cannot be guaranteed to read the new six-member lineup data, so a rollback restores the old program together with the database backup.
- The new program adds the Mission columns described above at startup, and eligible players get their tutorial restored when they load; no resource cache replacement or account reset is needed.
- To undo automatically restored mission state, stop the server and restore the program together with the pre-deployment database backup. Putting back only the old program does not undo saved mission state or reward flags; restoring the backup also discards progress made after it, so plan it within the deployment window.

## Known gaps

- This is not an Android client test; it cannot show that a loading hang has gone away on a real device. Mismatched keys are rejected explicitly; a client still needs the matching public/private key pair to log in. Historical Base64 accounts are not deleted or merged.
- Client pages, animations and the scene experience need verification on a real client, in particular: the costume model and equipment page; the character and light cone quick level-up UI; mission scripts and loading for the Qlipoth Fort floor changes; the client passing through Simulated Universe tutorial barriers, collisions and the settlement screen with its automatic exit request; the gallery UI and mission interaction; whether the black screen on entering a Simulated Universe battle is gone; restoring the story camera after the containment section monster attack; video playback; avatar frames and their display switch; the activity UIs.
- For the Qlipoth Fort, containment section and trial Trailblazer fixes, players retry by logging in again after the server is updated; no save reset is needed.
- The Discord Webhook of global chat sends no real request in the regression.
- Divergent Universe rooms are settled by clearing monsters in the scene, not by real battles.
- All challenge, avatar frame, ActivityBangboo and RealityShow checks are server-side only and do not replace verification on a real client.

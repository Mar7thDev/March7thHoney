# Proto

English | [简体中文](protobuf.zh-CN.md)

This document describes how the server's protocol definitions are stored, built and carried forward to a new client version. Read it before renaming protocol types or fields, regenerating command IDs, or upgrading to a new client.

Source: [`Proto/`](../../Proto/)

All protocol definitions the server uses are in one file, `Proto/StarRail.proto`. At build time `Proto.csproj` generates `obj/<configuration>/<framework>/protobuf/StarRail.cs` from it and compiles that; the generated C# is not under version control. `main` holds only the definitions for the current game version; definitions for older versions stay on their version branches.

## Layout

```text
Proto/
  StarRail.proto        all messages and enums of the current version; the build compiles this file directly
  overrides-manual.txt  manual decisions, one per line with evidence, for names that cannot follow by identity when carried
  cmdid-aliases.txt     command ID aliases: command name used by the server code = existing constant name
  Build/                MSBuild targets for automatic generation
  Tool/ProtoOrganizer/  tool that carries names to a new version and generates command ID constants
  obj/.../protobuf/     C# generated at build time, ignored by Git
```

The raw Demiurge dumps and carry reports are intermediate products and are not kept in the repository. Version branches for 4.8 and earlier still use the old layout, with one directory per version and grouping by `Cmd*Type`; the matching tools and documentation are on those branches.

## Format of StarRail.proto

- Only top-level `message` and `enum` definitions, sorted by name, with no `import` and no nested types.
- The comment on the first line records which client dump the file comes from.
- `// Obf:` before a type records its obfuscated name, and `// CmdID:` records the command ID that carries it. These two lines are what names are carried to the next version by; keep them when renaming by hand.
- Types and fields whose meaning has not been confirmed keep their 11-letter upper-case obfuscated names.
- The `Cmd<module>Type` enums are the command ID directories of each module; their members are named after the message carried by each command ID. They are generated by the tool and not referenced by any code.

To give an obfuscated name a meaningful name, edit this file directly; when renaming a type, also replace every field type that refers to it. Do not add or remove fields, or change field numbers or field types: these must match the client, and the next carry refuses to run if they do not (see below). After editing, build as usual; do not edit `obj/` by hand.

## Build and verification

```sh
dotnet restore March7thHoney.sln
dotnet build March7thHoney.sln -c Release --no-restore
python3 scripts/test-proto-generation.py
```

NuGet pins `Google.Protobuf.Tools 3.33.1` (protoc 33.1), matching the existing `Google.Protobuf 3.33.1` runtime; both versions are declared in `Directory.Packages.props` at the repository root. The first build needs to restore this tool package; the tool does not go into the server's published output. On Linux and Windows the host platform's tool is used, and cross-publishing does not change that choice. The macOS tool in this version is x64, so Apple Silicon needs Rosetta; alternatively `-p:ProtocolCompiler=<path>` can point to a protoc of exactly version 33.1.

The build target detects added, removed and modified schemas and missing generated files; when nothing has changed, generation is skipped. Building again after `dotnet clean` restores the generated code.

## Command IDs

`KcpSharp/CmdIds.cs` is generated by the tool from `StarRail.proto`: one constant per command ID, named after the message that carries it, followed by the aliases from `cmdid-aliases.txt`. Regenerate it after renaming a message that has `// CmdID:` or after adding or removing aliases:

```sh
dotnet run --project Proto/Tool/ProtoOrganizer -c Release -- cmdids
```

Aliases point to constant names rather than numbers, so the alias file does not need changes when command IDs change. `cmdids --check` only compares and does not write; `scripts/verify-security.py` uses it to confirm that the constants match the schema.

A command enum name is not necessarily the protobuf message type name: handlers bind to the current command constant and parse the real message type, so searching for a `message` with the same name as the enum member can miss the existing structure. When a request has no handler, the framework automatically sends an empty success response; that response cannot be taken as evidence that the feature ran.

## Upgrading to a new client version

Names can be carried across versions because obfuscated identities are stable between versions: a type's obfuscated name, property names and enum member names are the same in every version; only field numbers and cmdIds change. For a new client with the same obfuscation seed, update as follows, running every command from the repository root.

1. Use DemiurgeCSharp, a separate tool that dumps the client statically, to make a static dump (`demiurge proto`) of the new client's `GameAssembly.dll` and `global-metadata.dat`, which gives the raw definitions of the new version. Also have the raw dump of the current version ready: export it again, or take it from the version branch (for 4.8 it is `Proto/4.8/dumper/Raw/StarRail.proto` on the `4.8` branch).
2. Carry the reviewed names from the current file onto the new dump and write the result back to `Proto/StarRail.proto`:

   ```sh
   dotnet run --project Proto/Tool/ProtoOrganizer -c Release -- carry \
     --dump <new version dump> --prev-dump <current version dump> \
     --report <output path for the carry report> \
     --label "Demiurge static dump | Game Version: <version> (<client build>, GameAssembly link <date>)"
   ```

3. Regenerate the command IDs (`cmdids` from the previous section), build the whole solution and run the regressions.

`carry` carries names by obfuscated identity only: types by obfuscated name, fields by property name, enum members by member name. Field numbers and cmdIds are always taken from the new dump; old numbers are never reused.

- Before starting, it rebuilds the current `StarRail.proto` from the current version's dump, and continues only if the definitions match the file on disk line by line. Any manual change in the file that is not a pure rename (adding or removing fields, renumbering, changing types) is reported as an error at this step instead of being silently dropped.
- Types the current file does not include (non-protocol types such as `TrackInfo`) stay excluded; new types keep the names the dump gives them; an enum whose obfuscated name changed but whose member names and values are identical is treated as the same enum and listed one by one in the report.
- A field whose property name the client changed cannot follow by identity; in the report it shows up as a `-` paired with a `+` under the same message. Once evidence confirms that they are the same field, write it into `overrides-manual.txt` (`OBF.PROPERTY = field_name`, or `OBF = TypeName` for type names) together with the evidence; having the same type alone is not enough.
- An override entry that matches no definition is an error. Delete the entries left from the previous version before carrying; the names they gave are already in `StarRail.proto`.
- Command enum members are renamed every time from the new dump's command IDs; names from the previous version are not reused.

Update along with the upgrade:

- `GameConstants.GAME_VERSION`, set to the version the client reports for itself.
- The version-specific cmdId and field number assertions in `LoginSceneRegression` (VideoKeyInfo, SceneMapInfo, SyncServerSceneChangeNotify, the CommonRogueQuery branch, quick level-up, common lineups, classic Simulated Universe 18xx commands).

Never write an old version's cmdId numbers into a new version, and never decide a mapping from fields having the same type alone.

## 4.8 protocol notes

The current definitions come from a Demiurge static dump of the OSBETAWin4.7.51 client (`BinaryVersion.bytes` says `EngineReleaseV4.8`; GameAssembly linked on 2026-11-05). Protocol versions are named after the release version the test client corresponds to: 4.6.5x clients correspond to 4.7 and 4.7.5x clients to 4.8; `GameConstants.GAME_VERSION` is set to `4.7.51`, the version the client reports.

Changes from 4.7 to 4.8 (the full record is `Proto/4.8/migration-report.txt` on the `4.8` branch): of 2717 cmdIds, 2685 were renumbered; 4040 message fields were renumbered; 63 messages and 4 enums were added (all with obfuscated names, including two new command directories: `MFNJLCNMBON` for the Bangboo crossover `RPG.Client.ActivityBangboo` and `LDJDDDDPLLH` for DiceyDungeon `RPG.Client.DiceyDungeon`; see [DiceyDungeon](dicey-dungeon.md) for the latter's message and field mapping); 26 messages changed shape, mostly in GridFight. Three of these needed server changes:

- The obfuscated name of the kick type enum changed from `JNFDGPDHENJ` to `GGHJCJPPEFE`; members and values are unchanged.
- The oneof member of `GridFightSyncData` that carries `GridFightGameItemInfo` changed from property `GOOCHGKBIPN` to `JDGIAMABEME`; following the evidence in `overrides-manual.txt` it keeps the name `game_data_item_info`. This has not yet been confirmed on a real client.
- `GridFightPermanentGameInfo` dropped "last tutorial stage finished" `ENECKKGPKHI`, and `GridFightLastTutorialFinishScNotify` was removed along with it; the meaning of the new bool `PMFHAPIFFPO` is not confirmed and the server does not fill it.

Quick level-up is an example of a command enum name differing from the message type name: in 4.6, `KELLLHMHFHL` (376) corresponds to message `EKLIDIDKFHC`, and the captured response is `PMEMIDKDAFG` (357, enum `MILFFHPMLMN`); the same identities are 355/341 in 4.7 and 332/395 in 4.8. The 4.6 official server capture seq `36813-36829` can verify the request/response pairing and the level-up cost; its old command IDs cannot be used directly for later versions.

The Light Cone quick level-up identity is `EOBJKAMNNPI → AMNBMKEMMFL`. The 4.6 raw definitions mislabelled it as a duplicate `PromoteEquipmentCsReq/ScRsp`; the raw messages of official server seq `36852/36859/36927` decode to the target level, unique ID, EXP cost, ascension cost and ascension level respectively. From 4.7 on it maps to `EquipmentQuickUpCsReq/ScRsp` (513/517 in 4.7, 548/529 in 4.8): `IGOOJKMPMDC` is the target level, `KLMIBJIKIBB` the target ascension, `BOBOKJBAMNB` the EXP materials or fodder Light Cones, `IDGEEENIMMK` the ascension materials. Use the existing definitions by property identity; do not change it into `PromoteEquipmentCsReq`, which only performs ascension.
